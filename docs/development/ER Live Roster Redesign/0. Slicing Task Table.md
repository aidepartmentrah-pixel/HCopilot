## Background

HCopilot is being re-architected so ER intake is driven by a live
"who's currently in the ER" feed from 3iSoft (via a new endpoint on the
existing Hospital Directory API) instead of manual patient
search-and-add. Full raw source notes: `source/2026-9-18.md`,
`source/0. Intro.md`, `source/1. Building Requirement.md`. The proposed
endpoint's full field-by-field spec lives in the sibling
`RESTful-API-Integration` repo:
`versions/v1.2/requirements/5-er-current-visits-hcopilot/requirement.md`
(and `Hospital_Directory_API_OpenAPI_v1.2.yaml` alongside it).

## Confirmed decisions

1. **Contour Nurse** = the existing Beds Display / bed-overview role,
   not a third role. **Entrance Nurse** gets a new roster-driven
   Addition screen.
2. **Departure detection = "double departure."** A nurse's manual
   soft-departure is authoritative when it happens. The live-roster
   poll-diff is a safety net: when it fires, it **auto-discharges
   immediately** (not just a flag for review), tagged
   `departure_source="api_detected"` so it stays distinguishable from a
   nurse-confirmed discharge.
3. **Diff key = `er_visit_id`** — opaque, never parsed, never adopted as
   a primary key (same convention as `external_patient_id`).
4. **ID strategy**: HCopilot mints its own person/stay ID from the three
   name parts + a local stay id; `er_visit_id` is a reference field only.
5. **Manual search-and-add stays a permanent shortcut** (walk-ins, or
   whenever a nurse prefers it) — not merely an outage fallback.
6. **API decision**: one new endpoint, `GET /er/current-visits`, on the
   existing Hospital Directory API. Confirmed **not yet submitted to
   3iSoft** — internal-only ask so far (see peer-session update below).
   A **mock implementation is live now** — see "Dev/test endpoint"
   below — so slices are no longer blocked on the real vendor.
7. **Bedless population = computed, not a stored flag.** Membership is
   "any active `DailyPatients` row with no `patient_bed` relation."
   Unurgent's existing feature (OR-scheduler acuity-5 routing) **merges
   into this list** — `unurgent` becomes a display badge, not a gate.
   The standalone Unurgent nav item/section is removed.
8. **Triage Time** captured on the Addition/ISBAR screen, optional, same
   "blank until the event happens" treatment as `bed_occupation_time`.
9. **Roster-picked patients are created in HCopilot immediately on
   pick** — not deferred to final ISBAR submit. This needs a relaxed
   required-field set for roster-origin (`record_source="external"`)
   stays: name + `arrival_time` + `er_visit_id` only. Manually-typed
   (`record_source="local"`) stays keep today's stricter requirement
   (`name`, `gender`, `age`, `arrival_time`, `chiefcomplaint`, `acuity`)
   unchanged.
10. **History page = departed-only** (matches today's Log/archive
    framing). **Patients stays one top-level nav item**, split into two
    tabs: Addition and History (my call, per direct delegation — least
    disruptive, matches the existing Daily/Log toggle pattern users
    already know).
11. `encounter_type`, `section_name`/`administration_name`, and
    `/patients/first-names` are confirmed **unrelated** to this
    redesign — separate proposed items in the same v1.2 spec.
12. `bed_occupation_time` already auto-defaults to "now" the moment the
    assign-to-bed modal opens, but stays editable — whether "auto-set"
    should mean locking it read-only is still open (minor, not
    slice-blocking).

## Dev/test endpoint (from the `restful-api-integration-f9` peer session, 2026-09-18)

Real, live right now — not the vendor, a mock stand-in built the same
day this redesign started:

```
GET http://localhost:6001/api/directory/v1/er/current-visits
Header: X-API-Key: change_me
```

Confirmed response shape: `{success, items:[{er_visit_id, first_name,
father_name, last_name, arrival_time, gender, age, chief_complaint}],
total}` — `arrival_time` ISO-8601 with a real `+03:00` offset, ordered
ascending, no `limit`/`offset` accepted. **Caveat**: `gender`/`age`/
`chief_complaint` values in the mock are invented for realism, not
vendor-confirmed shapes — the mock is structurally correct, not
semantically authoritative. Treat accordingly in ER3/ER6/ER10.

**Vendor status**: not submitted to 3iSoft yet — this whole endpoint is
still an internal-only ask. No real timeline exists.

**New risk, not previously flagged, from the same session**:
`er_visit_id`'s stability across a whole visit is *assumed*, never
actually confirmed by the vendor. Design defensively — if a
previously-departed `er_visit_id` reappears in a later poll, treat it as
a **new** admission, never resume the old (now-archived) stay. Applies
to ER7.

   present, per its own "optional autofill only" design. Fixed by

   characteristic of the system, not a one-off to paper over.

persisted (e.g. derived fresh each time from whichever

sidesteps the restart problem entirely and is probably the better

after a soft-departure is a **new** admission, never a resumed stay —
diff logic must not try to "undo" an already-archived departure.
**Done when**: in a test harness, removing an item from a fake roster
between two calls discharges exactly that patient with

**Tested by**: unit test with a mocked `get_er_current_visits()`
