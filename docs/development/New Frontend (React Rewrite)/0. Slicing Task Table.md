## Background

Source: `source/HCopilot_New_Frontend_Master_Prompt.md` (verbatim) — a
full ground-up rebuild of HCopilot's frontend in React + TypeScript +
Vite, running **in parallel** with the existing vanilla-JS frontend,
against the **same backend and database**, no backend changes needed to
start. Not a redesign-in-place; the old frontend stays untouched as
fallback/reference until (and unless) the new one reaches parity and is
explicitly promoted.

Scope, per the master prompt: full design system (tokens, AppShell,
reusable component library), 5 feature pages (ER ISBAR Entry, Live ER
Board, History, Statistics, Settings), typed API layer, Vitest +
Playwright coverage, Arabic/RTL support, air-gapped-safe build, and
project documentation. This is large — realistically weeks of work, not
a single session, hence the same slice-and-track approach as the two
prior HCopilot initiatives.

## Real, confirmed environment facts (checked directly, not assumed)

- **CORS is already wide open** on the backend: `backend/app.py` has
  `CORSMiddleware` with `allow_origins=["*"]`. A new frontend on a
  separate port can call the existing API with **zero backend
  changes** to start.
- **Ports in use on this host** (checked via `docker ps`, 2026-09-21):
  1434, 1436, 5050–5052, 5433–5435, 6000, 6001, 8001, 8002, 8081, 8082
  (existing HCopilot frontend), 8088, 8090 (existing HCopilot backend),
  8110–8112. **8083 is free** — matches the master prompt's own
  suggested example port for the new frontend; use it unless a later
  slice finds a reason not to.
- **Node.js 24 / npm are already installed** on this host (confirmed
  during the ER Live-Roster Redesign's Playwright work) — no new
  runtime dependency to install for local dev.
- The existing frontend (`frontend/`) is plain HTML/CSS/JS with no
  build step, served by nginx in production
  (`frontend/Dockerfile`/`nginx.conf`) — the new frontend needs its own
  Dockerfile (multi-stage Vite build → static serve) and its own
  `docker-compose.yml` service entry, additive, not replacing the
  existing `frontend` service.

default `http://localhost:8090`) so the same relative-path code works
identically in `npm run dev` and in the built/nginx-served app.
`VITE_API_BASE_URL` is kept as an explicit (currently-empty) escape
hatch, not deleted, in case a future non-proxied deployment needs it.

meaning/behavior) — documented here rather than silently made.

Fixed properly, not just for this one table: added real TanStack
Table pagination to `DataTable` itself (`pageSize` prop, default 20,
`pageSize={0}` opt-out for a page that genuinely needs every row),
with Previous/Next controls and a "Page X of Y (N total)" indicator —
benefits every table in the app at once (Active Patients, History,
all 4 Settings resources), not just the one screenshot happened to
catch. 4 new `DataTable.test.tsx` cases cover it directly (correct
row count per page, Next/Previous navigation, controls hidden when
everything already fits on one page, `pageSize={0}` opts out cleanly).

**Real regression the pagination fix itself caused, found immediately
by re-running the full suite, not assumed safe**: 4 existing tests
broke — a freshly-created patient/ward no longer reliably landed on
page 1 of its own table (with 236 existing Active Patients and several
prior sessions' leftover test wards, a new row could easily land on
page 12+), so "reload and re-select the patient I just saved" and
"the ward I just added is visible" both failed. This wasn't only a
test problem — a real hospital user who just added a ward would have
the identical experience of not being able to find it. Fixed with a
real product decision, not a test workaround: added a `defaultSort`
prop to `DataTable` and set the Active Patients table to sort by
`arrival_time` descending (also more clinically useful — most
recent arrival first) and the Wards table by `ward_id` descending.
Confirmed by running the **entire** e2e suite twice after the fix,
not just the previously-broken specs — 32/32 both times.

**NF8.5 — Air-gapped, a real network-blocked check, not just a
static grep.** `airgapped.spec.ts`: routes every request through a
Playwright interceptor that aborts anything not resolving to
`localhost`/`127.0.0.1` and records what it blocked, across both the
app shell and an Arabic-name-heavy page (exercises the actual
`@font-face` requests) — asserts zero external requests were even
attempted, a real behavioral proof rather than NF0.5's static
`grep` over `dist/`. A second spec confirms every `@font-face` rule's
`src` resolves to this app's own origin, never
`fonts.googleapis.com`/`fonts.gstatic.com`.

**Real test-flakiness found and fixed properly, not papered over**:
that second check originally sniffed live `page.on('request')` events
for font URLs — passed in isolation, failed intermittently after the
rest of the suite ran first (0 font requests observed), because
Chromium's disk cache served the already-fetched font with no network
activity for that specific test. First attempt fixed it with a CDP
`Network.setCacheDisabled` call — this **still** failed on a later
full-suite run, proving cache-disabling alone wasn't sufficient
(the underlying flakiness was about timing/caching behavior more
subtle than one CDP flag). Rather than keep patching the same
network-sniffing approach a third time, changed strategy entirely:
`page.evaluate()` reads the actual computed `@font-face` rules
straight from `document.styleSheets` and checks what the browser
resolved each `src` to — deterministic, since it doesn't depend on
whether a fresh network request happened to fire during that
particular test. Confirmed with two full-suite runs, back to back,
both 32/32 — the standard this project holds itself to when a fix's
first attempt turns out to be incomplete: keep verifying until it's
actually reliable, not until it looks reliable once.

**Final verification, real commands, all green**: `npm run lint` (0
warnings), `npm run build` (clean), `npm run test`
(`Tests  52 passed (52)`, +3 from `DataTable`'s new pagination cases),
`npm run test:e2e` — **32/32 passing, run twice for stability**
(9 new specs across `rtl.spec.ts`/`airgapped.spec.ts`/
`visual-regression.spec.ts`, plus every prior spec from NF3-NF7 still
green after the pagination/sort changes). A standalone contrast
calculation and multiple real screenshots (reviewed, not just
asserted) did the real work this phase — between them they found 2
non-trivial bugs (the AA contrast failures, the missing pagination)
that a green test suite alone had not caught.
