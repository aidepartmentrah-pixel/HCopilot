# HCopilot New Frontend — Global Theme & Application Shell Requirements

## Purpose

The current new frontend is functionally cleaner than the old frontend, but visually it still feels unfinished, empty, and too close to a starter application.

The goal is not to redesign individual pages independently.

The entire application must first establish a **single strong visual identity and reusable application shell**.

Every page should feel like part of the same mature hospital product.

The desired product type is:

> **A modern clinical operations application with a strong branded shell and a clean, information-rich operational workspace.**

It must not feel like:

- a generic admin template
- a student dashboard
- a collection of unrelated pages
- a blank navigation launcher
- an overly minimalist application with huge unused areas
- a decorative marketing website
- an emoji-based interface

---

# 1. Global Visual Direction

Use the following visual concept:

## Branded Indigo Clinical Shell + Neutral Operational Workspace

The product should visually consist of two layers.

### Layer 1 — Application Shell

Strong HCopilot identity.

Includes:

- branded indigo/navy top bar
- HCopilot product icon
- HCopilot wordmark
- primary navigation
- global search
- notification area
- user identity and role

### Layer 2 — Workspace

Calm and neutral.

Use:

- very light gray / off-white page background
- white panels and surfaces
- subtle borders
- restrained shadows
- dark slate typography
- indigo for interaction/selection
- semantic colors only where they communicate meaning

Do not return to the old pattern of using a saturated purple background across the entire page.

---

# 2. Color Philosophy

Indigo should remain the visual identity of HCopilot.

However, indigo must represent:

- brand
- selection
- active navigation
- primary actions
- interactive emphasis

It should NOT represent every operational state.

Clinical and operational meanings need their own semantic colors.

Recommended roles:

- Indigo / blue-indigo → brand, selection, primary actions
- Green → available / success / operational
- Amber → attention / waiting / warning
- Red → critical / destructive / abnormal
- Muted coral/red → occupied
- Slate gray → disabled / secondary / neutral
- White / pale slate → workspace and surfaces

Color should never be the only indicator of state.

Always combine important colors with:

- labels
- icons
- text
- status badges

---

# 3. Top Bar — Global Requirement

The top bar is one of the most important parts of the new frontend.

It must be implemented once as a reusable global component.

Suggested component:

`AppShell / TopNavigation`

The top bar must remain identical across:

- Home
- ER ISBAR Entry
- Live ER
- History
- Statistics
- Settings
- future pages

Individual pages must not redefine:

- navbar height
- icon sizes
- padding
- active-state design
- user area
- search design
- branding location

---

# 4. Top Bar Visual Character

The currently implemented white/light navigation feels too weak.

The preferred direction is the stronger indigo/navy top bar demonstrated in the newer mockups.

The header should feel:

- premium
- clinical
- modern
- confident
- restrained
- clearly branded

It should not become excessively dark or visually heavy.

The main body below it remains light.

---

# 5. HCopilot Product Icon

Create a dedicated HCopilot application icon.

Do not rely only on plain text saying `HCopilot`.

Do not make the hospital logo the primary product identity.

The application should have its own recognizable symbol.

Desired qualities:

- simple
- geometric
- scalable
- recognizable at small sizes
- appropriate for healthcare
- consistent with the indigo brand
- usable in navbar, favicon, login screen, footer, documentation, etc.

A medical cross / connected-care / abstract H-shaped concept is appropriate.

Avoid an overly literal or clip-art-style medical icon.

The icon should be paired with:

**HCopilot**

and optionally a small product tagline such as:

> Smarter ER Care. Together.

Hospital branding can appear separately when required.

---

# 6. Top Bar Structure

Recommended structure:

text
┌──────────────────────────────────────────────────────────────────────────┐
│ HCopilot  │ Home │ ER │ Patients │ Tasks │ Reports │ Resources        │
│           │                                      Search                │
│                                                Bell  User ▾            │
└──────────────────────────────────────────────────────────────────────────┘


Actual navigation labels should match implemented modules.

The structure should remain stable.

---

# 7. Navigation

Navigation should use:

- one consistent icon family
- compact text labels
- clear active state
- subtle hover states
- consistent spacing

The selected page should have a clearly visible but restrained active treatment.

Example:

- lighter indigo background
- slightly brighter border/underline
- white or high-contrast text/icon

Avoid oversized tab pills.

Avoid every item looking like a separate button.

---

# 8. Global Search

Add a global search field to the top bar.

Purpose:

- search patients
- MRN / patient ID
- visit/stay ID where supported
- potentially keywords later

Example placeholder:

> Search patients, MRN, or keywords...

The search must visually belong to the top bar and appear consistently across application pages.

If functionality is not yet complete, the UI architecture should still reserve the correct location for it rather than redesigning the navbar later.

---

# 9. Notification Area

Add a notification bell.

The notification area should support:

- unread indicator
- count badge when appropriate
- hover/click state

The design should remain subtle.

Example:

`Bell icon + small red badge`

Do not use aggressive animation.

---

# 10. User Identity Area

Replace the current placeholder-style circular `U` with a proper user identity block.

The top-right area should communicate:

- avatar or initials
- user name
- professional role or department
- dropdown indicator

Example:


[avatar] Dr. Sarah Chen
         Emergency Medicine    ▾


or for the hospital context:


[initials] Jamie Smith, RN
           Emergency Department ▾


If no profile photograph exists, use a clean initials avatar.

The user block must not feel like a temporary placeholder.

---

# 11. Hospital Context

Where useful, the interface may display:

- hospital/site name
- current date/time

These do not need to dominate the navbar.

They can appear in the page header area on pages such as Home.

Example:


Tue, Apr 22, 2026
10:24 AM
Al-Rassoul Al-Aazam Hospital


Use actual deployment data when available.



# 12. Icon System

Use one professional SVG icon family throughout the new frontend.

Recommended:

**Lucide React**

Do not use emoji as production interface icons.

Avoid:

- 🏥
- 📋
- 🛏️
- 👤
- 🔴
- 🟢
- ❤️
- 🌡️

as UI graphics.

Semantic status dots may still be used where appropriate, but they should be CSS/SVG UI elements rather than Unicode decoration.

Icon rules:

- same stroke weight
- same family
- consistent size
- no random decorative icons
- icons must aid recognition

Approximate sizing:

- 16–18 px → controls
- 18–20 px → navigation
- 20–22 px → section/object identity
- 24–32 px → meaningful empty states only



# 13. Typography

Use typography rather than excessive cards/colors to create hierarchy.

Recommended:

- Inter for English/Latin UI
- Noto Sans Arabic or compatible professional Arabic font for Arabic content

Suggested hierarchy:

- Page title: 28–32 px
- Major section heading: 20–22 px
- Section/card title: 16–18 px
- Body: 14–15 px
- Form/table labels: 12–13 px
- Metadata: 12–13 px
- KPI values: 26–32 px

Arabic names must render correctly and naturally.



# 14. Page Background and Surfaces

Use a neutral page canvas.

Recommended visual hierarchy:

Indigo top shell
↓
Light gray / off-white canvas
↓
White content surfaces
↓
Subtle gray borders


Avoid:

- large purple background blocks
- huge empty white spaces
- excessive gradients
- glassmorphism
- neon effects
- strong shadows

Use restrained shadows only when they meaningfully separate layers.

---

# 15. Cards

Do not make every UI element a card.

Cards should represent meaningful units.

Good uses:

- KPI
- patient summary
- alert
- chart
- ward/placement area
- record preview

Avoid:

- page inside card
- section inside card inside another card
- every button as card
- every row as decorative card

Moderate corner radius should be standardized globally.

---

# 16. Spacing

Use a consistent spacing scale.

Recommended:


4

All pages must share:

- page margins
- component padding
- control heights
- section gaps
- card radius
- table row density

Avoid page-specific arbitrary spacing.

---

# 17. Page Headers

Use one reusable PageHeader pattern.

Example:


HCopilot Overview
Central workspace for ER operations and hospital insights.


or:

Create a new structured handover for an ER patient.


Actions appear on the right when necessary.

Do not place every page title inside a large white decorative container.

---

# 18. Home Page Identity

The Home page must NOT remain a four-card navigation launcher.

The current implementation answers:

> Where would you like to go?

The required Home page should primarily answer:

> What is happening in the ER right now?

Therefore Home should function as an:

## Operational ER Overview Dashboard

Quick actions remain useful but become one section of the dashboard, not the complete page.

# 19. Home Page Recommended Structure

Recommended layout:

# 20. Welcome / Hero Area

A branded welcome section is desirable because it gives the product identity and visual polish.

- informational
- warning

Other pages may legitimately have different density based on their purpose.

The new History page should be optimized for:

- finding previous ER stays
- quickly moving between records
- reviewing historical ISBAR information
- opening a complete record when deeper inspection is required
- performing allowed actions such as View, Edit, and Delete

The result should feel like a professional clinical record browser rather than a plain database table.

---

> What happened during previous ER stays?

History is primarily a retrieval and review workspace.

## Mission

Restore the missing **Flow Prediction** capability in the new React + TypeScript HCopilot frontend, but redesign it so the frontend is not permanently hardwired around one specific model or one prediction task.

The old HCopilot already had a useful first-generation Flow Prediction page with:

- 30 / 60 / 90 day forecast horizons
- Average Daily Patients
- Max Daily Patients
- Min Daily Patients
- Total Records
- a large Historical vs Predicted patient-flow chart

That functionality must not disappear.

However, the new frontend should prepare for future HCopilot development where the collected ER data may be used to train multiple prediction models for different tasks.

The new architecture should therefore separate:

- operational predictions,
- statistics/analytics,
- model administration/training.

The core principle is:

> Statistics explains what happened.
>
> Predictions estimates what may happen next.
>
> AI & Models manages how prediction models are trained and promoted.
