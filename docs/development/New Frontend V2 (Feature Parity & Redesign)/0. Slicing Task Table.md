## Standing rules (apply to every slice)

- **Never fabricate data.** The source spec's mockup images (and the two
  ChatGPT-generated logo images at `C:\Users\it\Downloads\ChatGPT Image Sep
  22, 2026, *.png`) are layout/flow/"feel" references only. Every number,
  label, alert, or trend shown in the UI must trace to a real backend field —
  the source spec itself says this explicitly, repeatedly, per page ("Do not
  fabricate statistics purely for visual completeness", etc.). If a mockup
  implies data that doesn't exist yet (a % trend with no historical baseline,
  a PACS/LIS status HCopilot doesn't integrate with), omit it or use the
  documented empty/unavailable state — never invent it.
- **No emoji as UI graphics.** Lucide React only, per the source spec's own
  icon-system section, and per the existing `frontend-new` convention.
- **CSS Modules, no styling library** — same as NF0–NF9.
- **`dir="auto"` on patient-name-bearing fields** — Arabic names are a
  first-class case on every page touched here, not just ISBAR.
- **Air-gapped**: any new dependency (a charting library for Statistics/
  Predictions, the two logo PNGs, any new font) must be locally bundled and
  re-verified against `e2e/airgapped.spec.ts`. Flag a new runtime dependency
  before adding it rather than silently vendoring one.
- **A slice is not done until its tests are, and both pass twice in a row**
  (this project's own standing discipline from NF8 — a fix that only "looks"
  fixed once isn't trusted here).
- **Testing shape per slice**: Vitest + RTL for new components/pure logic
  (aggregation math, formatting, control state machines) — colocated, same
  as existing `frontend-new/src/**/*.test.tsx`. Playwright e2e against the
  real backend for user flows — extend the existing spec files or add one
  per page, same `fullyParallel: false, workers: 1` convention (the
  `/api/patients/next-ids` race is still unfixed backend-side). Where a
  slice's UI depends on a backend endpoint not yet exercised by
  `frontend-new` (e.g. Hospital Directory settings, model training/
  promotion, accounts), add a small smoke check (a Playwright test or a
  quick `curl`/pytest hit) that confirms the endpoint's real response shape
  *before* building the page against an assumed shape — don't guess the
  contract from the old frontend's JS and hope.
- **Don't touch `frontend/` (old) or `backend/` behavior** unless a slice
  explicitly requires a real, missing backend capability — check first
  whether the data already exists via another endpoint (most of this spec's
  "missing" functionality is old-frontend-only UI, not missing backend).
- **One commit per completed slice** (or per natural sub-slice for V2.2),
  same granularity discipline as the first mission's NF-slices. Do not merge
  to `main` or push — that decision belongs to the user.
- Log every slice here the same way NF0–NF9 were logged: a dated entry under
  the slice with what was actually done, real command/test output, bugs
  found, scope decisions made. This table is the authoritative progress
  record — update it as you go, not at the end.

**Two real bugs found and fixed while building/testing this — not
cosmetic, both affect real workflow correctness**:

1. **Clinical-safety-adjacent data bug in `Select` (pre-existing, not
   introduced by this slice, but this slice's status-tracking is what
   surfaced it)**: `components/forms/Select.tsx`'s placeholder option was
   `<option value="" disabled hidden>`. Per the HTML spec, when a
   `<select>` mounts with no explicit `selected`/programmatic `.value` set
   (true for every untouched optional field — react-hook-form only
   applies a *defined* default via the field's ref callback), the browser
   auto-selects the first **non-disabled** option — silently landing on
   real clinical defaults: ESI "1 — Immediate", Clinical Status "Stable",
   Neuro Status "Alert", Allergies "Yes", Isolation "None", Swallow
   Assessment "Passed", Voiding "Independent", Discharge Plan "home", O2
   Support "room air" — for a field the user never touched. Confirmed via
   a throwaway debug spec dumping `getValues()`: a completely untouched
   draft's `acuity` read back as `1` and `isbar.clinical_status` as
   `"Stable"` the moment any validation ran. **Fix**: removed `disabled`
   from the placeholder option (kept `hidden`, which still excludes it
   from the open dropdown list) — the browser then correctly defaults to
   the placeholder itself, matching what the UI visually showed all
   along. One-line fix, single shared component, so it corrects every
   affected select across Patient & Arrival/Vitals/Situation/Background/
   Focused Assessment/Recommendation at once. Flagging this explicitly:
   this means any ISBAR record saved before this fix, via a field left
   untouched, may have silently stored one of these phantom defaults
   instead of a real null/unset value — not fixed retroactively here
   (out of scope for a frontend slice; noting it for whoever owns data
   backfill/audit decisions).

2. **Race condition in this slice's own new live-revalidation logic**: the
   first implementation re-ran `trigger()` on every keystroke inside a
   `methods.watch()`-driven effect. Confirmed via the same debug-logging
   approach that overlapping `trigger()` calls (typing fast, or a field
   change immediately followed by clicking Continue) could leave an
   earlier call's promise resolving *after* a newer one and clobbering its
   result — a section correctly marked Complete by Continue would get
   silently downgraded moments later by a stale, already-superseded
   validation pass. Debouncing alone didn't fully fix it (a timer already
   ticking down before Continue is clicked can still fire after). Fixed by
   redesigning: async re-validation now runs on **blur** (via one
   delegated `onBlur` on the workspace `<form>`, mapping the blurred
   field's `id` back to its owning section) plus once on manually
   reopening an already-attempted section — both naturally sparse,
   non-overlapping triggers — backed by a `generationRef` counter so even
   if two calls somehow overlap, only the one that started last is allowed
   to apply its result. The cheap not-started→in-progress flip stayed
   keystroke-driven since it's synchronous and has no `trigger()` call to
   race.
