## Background

Source: `source/UI Decision we Need to decide.md` (the full decision
doc, verbatim) + `source/mockups/` (3 reference mockups — Option 1 for
the ISBAR entry page, Option 5 for the Live ER Board, Option 4 for
History). These mockups are generic design-tool output (different nav
chrome, branding, icons than HCopilot's real UI) — treat them as
**layout/interaction references**, not pixel specs to replicate
literally. HCopilot has its own existing design system; match that,
not the mockup's colors/fonts/nav bar.

The doc defines 3 page-level architecture decisions, replacing the
single combined "Patients" page + Beds Display's bedless section that
`er-live-roster-redesign` (ER8/ER9) just built:

- **Page A — New Patient/ISBAR**: live roster + ISBAR form, form
  disabled until a patient is selected, no modal.
- **Page B — Live ER Board**: beds and no-bed patients share one card
  component, arranged in horizontal lanes per ward/area, plus a
  waiting-time attention treatment.
- **Page C — History**: table + persistent resizable right-side
  preview pane (not a modal), with a full-page escape hatch for deep
  review/print/export/edit.

## How this relates to the ER Live-Roster Redesign (already DONE)

**This redesigns the UI layer on top of live-roster work that's
already built and tested — it does not redo the backend.** Keep,
unchanged, unless a slice below says otherwise:

- The roster fetch (`GET /api/hospital-directory/er/current-visits`),
  the relaxed-required create path (`record_source="external"` +
  `er_visit_id`), the shared `discharge_active_stay()`, the bedless
  computed-membership endpoint (`GET /api/beds/bedless`), the 2-minute
  poll-diff safety net, `triage_time`/`er_visit_id`/`departure_source`
  columns — all backend, all real, all covered by
  `backend/tests/test_er_redesign.py`. Reuse it; don't rebuild it.
- What's changing is **how these are surfaced in the UI** — the
  roster-picker-into-a-modal pattern (ER9) and the flat bedless-card-
  list-under-the-bed-grid pattern (ER8) are exactly what this redesign
  replaces with Page A and Page B respectively.

## Real conflicts found against the already-built ER8/ER9 UI — flag, don't silently resolve

A prior session (this one) read both the new decision doc and its own
just-finished ER8/ER9 code closely enough to find 3 real tensions.
None are blocking — each has a recommended default — but the next
session should confirm with the user before building, not guess
silently:

1. **Does picking a roster patient still create the HCopilot record
   immediately, or does an explicit "Start ISBAR" action create it?**
   The decision doc's own prose says selection immediately "starts the
   encounter/stay" (step 1 of the Decision 1 flow) — consistent with
   the already-confirmed "create on pick" decision from the ER
   Live-Roster Redesign. But the Option 1 mockup shows a "Start ISBAR"
   button that *reads* like the actual creation trigger, with fields
   pre-loaded but a visible confirm step before anything is saved.
   **Recommendation: keep "create on pick," per the doc's own explicit
   text** — the mockup's button is most likely generic template
   chrome, not a deliberate second confirmation step (which the doc's
   own Decision 1 rationale explicitly argues against — "there should
   not normally be an additional confirmation modal/step"). Confirm
   with the user before building either way.

   **CONFIRMED by user, 2026-09-21: create on pick.** Backend record
   creation happens immediately on roster-patient selection (existing
   relaxed-required `/api/patients/add` path). Refinement found on
   actually viewing the Option 1 mockup image directly (not just its
   text description): the "Start ISBAR" button is styled as a real,
   deliberate primary CTA (colored/enabled) next to a disabled "Save
   Draft" — not decorative chrome as guessed above. Resolution: keep
   it, but purely as a **UI-side** state transition (pre-filled
   disabled preview → active editable accordion), decoupled from
   backend creation timing. No second network confirmation step.
2. **Per-ward waiting lanes need a backend concept that doesn't exist
   yet.** The Option 5 mockup shows waiting (no-bed) patients
   appearing *inside* specific ward lanes (e.g. a waiting patient
   inside the "Emergency (Main ER)" lane, another inside "Trauma").
   Today, a bedless patient has **no ward association at all** —
   `DailyPatient.admission_ward_id` is only ever set once a bed is
   actually assigned (`BedManager.add_bed_to_history()`). Putting a
   waiting patient in a specific ward's lane would need a new concept
   — a nurse pre-assigning a target ward/area before a specific bed —
   which is real, new backend+UI work, not just a layout change.
   **Recommendation: build the simpler reading the doc's own text
   explicitly allows** — one catch-all "Waiting / No Bed" lane for
   every bedless patient (matching `GET /api/beds/bedless` exactly, no
   backend change needed), not per-ward waiting slots. The doc's own
   words: *"A separate Waiting/No Bed lane **may also** exist for
   patients who are not associated with a particular ER area"* —
   phrased as the normal case, not a special case. Confirm with the
   user; per-ward waiting is a real, larger follow-up if wanted.

   **CONFIRMED by user, 2026-09-21: catch-all lane.** One "Waiting/No
   Bed" lane, sourced from `GET /api/beds/bedless` unchanged. Refinement
   found on viewing the Option 5 mockup directly: it actually shows a
   *hybrid* — per-ward waiting cards (W01–W04) embedded inside ward
   lanes **and** a separate bottom catch-all queue (W05–W10) — not
   purely per-ward as the text description alone suggested. Since
   we're building catch-all-only, ward lane headers show bed counts
   only (no "· N waiting" sub-count); every bedless patient renders
   solely in the one bottom lane. Per-ward waiting slots remain a real,
   larger follow-up if wanted later.
3. **"5 minutes without being handled" needs a concrete definition to
   build against.** The doc leaves this deliberately vague ("the exact
   visual treatment can be decided later") but the *threshold
   condition itself* ("without being handled") still needs a real
   field to compute from. **Recommendation: define "handled" as
   `triage_time` being set** — ER10 already added this exact column
   for exactly this purpose (documented there as "for ER wait-time
   KPIs"), so "waiting > 5 min" becomes `now - arrival_time > 5min AND
   triage_time IS NULL`, no new backend field needed. Confirm with the
   user — an alternative reading is "no bed assigned yet" instead of
   "not triaged," which is a different (also already-available) signal
   and would change which patients get flagged.

   **CONFIRMED by user, 2026-09-21: `triage_time IS NOT NULL`.**
   Waiting-alert condition: `now - arrival_time > 5min AND triage_time
   IS NULL`.

## Confirmed decisions (from the source doc — not open questions)

1. Page A's form is **disabled, not hidden**, before patient selection
   — visible structure, inactive inputs, explicit "no patient
   selected" state text.
2. Once selected: patient identity banner is prominent (name, age,
   gender, arrival, patient #) with a **"Change Patient"** action —
   explicit anti-wrong-patient-entry safety, not just nice-to-have.
3. The 6 ISBAR sections stay accordion-style, unchanged in content —
   this is a page-layout change, not an ISBAR-fields change.
4. Directory search / manual entry become a visually secondary
   fallback ("Can't find the patient? Search Hospital Directory ·
   Manual Entry"), not competing for space with the roster.
5. Page B: bed cards and no-bed-patient cards share one component
   family — same dimensions, radius, spacing, typography, interaction
   locations. Only the icon (bed vs. seated-person) and status
   treatment differ.
6. Page B: horizontal lanes, grouped by ward/area (see open question 2
   above for exactly how bedless patients slot in).
7. Page B: summary stat row (Total/Occupied/Available/Without
   Bed/Waiting>5min) at the top, doesn't replace the board itself.
8. Page B: soft departure removes the patient from the board
   immediately (already true today via `notifyDataChange`/`loadBeds()`
   refresh — confirm it still holds after the lane restructure, don't
   assume).
9. Page C: table + **persistent** (not modal) right-side preview pane,
   resizable via a draggable divider, roughly 60–65% table / 35–40%
   preview by default, with sane minimum widths on both sides.
10. Page C: preview pane shows patient summary + all 6 ISBAR sections
    in compact/collapsed form; a **"Open Full Record"** action opens a
    dedicated full-width page for long text, print, export, and
    editing. Preview pane itself stays inspection/navigation-focused,
    not the primary editing surface.
11. Page C: closing the preview returns the table to full width without
    losing search/filter/scroll state.
12. Each page answers exactly one question and shouldn't grow into the
    others' responsibility (doc's own closing principle) — worth
    keeping in mind for every future addition, not just this pass.

## Testing design

Same conventions as the ER Live-Roster Redesign — extend the existing
suites, don't invent new infrastructure:

- **Automated UI**: this wave is almost entirely frontend, so
  Playwright carries most of the verification weight — new spec files
  per page (`frontend/tests/*.spec.js`), following the already-
  established helpers.js pattern (`login`, `gotoPatients`,
  `gotoBedsDisplay`, add a `gotoHistory` alongside). Real
  browser-driven proof, not just unit-level DOM assertions — actually
  run `npx playwright test` after each slice and paste the real
  pass/fail counts into this doc's log, the same way the ER
  Live-Roster Redesign log did.
- **Backend**: only touched if open questions 2 or 3 resolve toward
  adding a new field (e.g. a target-ward pre-assignment concept) —
  most slices need zero backend change. If any backend change does
  turn out to be needed, follow the exact same pattern as
  `backend/tests/test_er_redesign.py` (real `TestClient(app)`, real DB
  writes, `finally` cleanup).
- Full regression: re-run the **entire** existing Playwright suite
  (11 specs as of ER1–ER12's close) after every slice, not just the
  new spec — this UI wave touches the same pages
  `isbar-form.spec.js`/`patient-details.spec.js`/`addition-roster.
  spec.js`/`beds-bedless.spec.js`/`er-departure-safety-net.spec.js`
  already cover, so regressions are the real risk, not just new bugs.

**Design decision revised after building (recorded here, not silently
dropped)**: the tracking doc's earlier note (UI0, above) speculated
about keeping a separate "Start ISBAR" button as a pure UI-side state
transition, reasoning from the Option 1 mockup's button styling alone.
After actually building the disabled→active flow, this was dropped —
the single mockup screenshot only shows the *before-selection* state
("Select a patient… to begin"), never an intermediate
"previewed-but-not-yet-started" state, so there was nothing concrete to
build against. Simpler and more faithful to the doc's own explicit text
("selection immediately starts the encounter"): picking a roster row
both creates the record *and* activates the panel in the same action,
no extra click.

**Scope decision**: the "Active Patients" table (formerly the
Addition-tab's dataset table) stays on Page A below the two-panel
layout — the doc's Page A description doesn't mention it, but removing
it would drop the only way to resume a non-roster-origin (manual/
directory) in-progress stay, since those never appear in the roster
list. Its Edit action now calls `selectPatStay()` instead of opening
the old edit modal (consistent with Page A's "no modal" principle);
View still opens the existing read-only details modal, unchanged
(out of scope for Page A — Page C/UI-C2 is where that modal's rendering
logic gets extracted and reused).

**Real bug found by running the suite, not by inspection** (matching
the standard the prior ER Live-Roster Redesign session held itself to):
`initPatientForm()`'s `loadNextPatientIds()`/`loadPatErRoster()` calls
were fire-and-forget (never awaited). The original ER9 code was immune
to this because a roster pick populated the separate `pedit-*` edit-
modal fields, untouched by `loadNextPatientIds()`. This redesign reuses
the same `pat-*` fields for both a fresh draft and an active stay, so
the race became live: `pickPatErRosterItem()`/`createPatientFromForm()`
call `await loadPatients()` then populate `#pat-patient-id`/
`#pat-stay-id` with the real created stay's id via `selectPatStay()` —
but the unawaited `loadNextPatientIds()` GET could still resolve
*afterward* and clobber those fields back to "next available"
placeholder values. Caught by `addition-roster.spec.js` and
`er-departure-safety-net.spec.js` failing with `details.record_source`/
`details.source` coming back `undefined` (the test had read a stay_id
that didn't correspond to any real record). Fixed by making
`initPatientForm()` `async` and awaiting both calls, and awaiting it
from `loadPatients()`.

**Also found**: `.pat-add-footer`'s own `display: flex` rule (declared
in both `patients.css` and `patient-isbar-form.css`) beat the UA
`[hidden]` rule at equal specificity, so toggling the `hidden` attribute
on the footer via `setPatFormMode()` had no visual effect — caught by
the first Playwright run (`toBeHidden()` failed while the DOM inspector
showed `hidden=""` present). Fixed with an `#pat-a-footer[hidden] {
display: none; }` override, the same pattern already used for the
placeholder/banner/roster-list.

- Waiting-time attention treatment (UI-B5): `_erbIsWaitingOverThreshold()`
  = `triage_time` still null AND arrival more than 5 minutes ago — the
  confirmed answer to open question 3, reusing the `triage_time` column
  ER10 already added. Flagged cards get an amber outline + pulse

**Scope decision**: a waiting card's only action is still "click → open
the discharge modal" (`openBedlessDischargeModal`), same as the old

Also dropped: the old bedless-only search box (`#bedless-search`) has

regression, noted rather than silently dropped; a board-wide search
across all lanes would be the natural follow-up if wanted.

**Real bugs found by running the suite, not by inspection:**
1. A waiting card with a long, unbroken name/complaint string rendered
   at ~290px instead of the intended 168px, while a bed card sitting in
   the exact same `.erb-card` class rendered correctly at 168px. Cause:
   flexbox's default content-based automatic minimum width wins over
   `flex: 0 0 168px` when inner text can't wrap — `white-space:nowrap`
   on `.erb-card-name` doesn't stop the ancestor flex item itself from
   growing to fit that text unless the flex item also has `min-width:
   0`. Fixed by adding `min-width: 0` to `.erb-card`. Caught by
   `beds-lanes.spec.js`'s dimension-parity test comparing real
   `boundingBox()` widths, not just class names.
2. `check_required_by_origin` (`patient_management/api.py`) is a
   `model_validator` on `_PatientBase`, so it re-runs on every PUT
   `/modify` too, re-deriving roster-origin from *that request's own*
   `record_source`/`er_visit_id` fields — not from anything already
   stored. Both `saveActivePatientForm()` (new, Page A) and the
   pre-existing `saveEditPatient()` (ER9, still reachable via View →
   "Edit Patient Data" for daily stays) built their PUT payloads
   without those two fields, so a roster-origin stay's incremental save
   always 422'd demanding gender/age/acuity/chiefcomplaint — even
   though each function's own client-side check correctly judged them
   optional. Confirmed live against the running backend with `curl`
   before fixing. Fixed both call sites by resending
   `record_source`/the real `er_visit_id` (tracked in new
   `patActiveErVisitId`/`patEditErVisitId` variables) whenever the
   roster-origin flag is true. This is a pre-existing ER9 bug, not
   introduced by this redesign, but directly adjacent to code this pass
   touches — fixed rather than left for a future session to
   rediscover. New regression test in `addition-roster.spec.js` proves
   a roster-origin partial save (only a vital touched, no identity
   fields) succeeds.

  text, filter selections, pagination, and scroll position all survive
  by construction, not by special-cased restore logic.

**Scope decisions (named, not silently dropped):**
- No "Status" filter — every row in this table is already Discharged by
  definition (that's what makes it History), so a status dropdown would
  have exactly one meaningful value. Acuity, Bed, and arrival-date-range
  are the three real dimensions built instead.
- The mockup's single "All Dates" dropdown became an explicit From/To
  date-range pair — more precise than a preset-buckets dropdown, and
  HCopilot has no existing "date bucket" component to match against.
- The preview pane's own stale content isn't re-fetched on an unrelated
  background data change (only the table re-renders, via the same
  `onDataChange` convention `patients.js`/`beds_display.js` already use)
  — acceptable since the preview shows a snapshot of one already-closed,
  immutable-in-practice discharged stay; re-opening it re-fetches fresh.
- Editing a discharged stay still opens the pre-existing log-patient
  modal (`openEditPatientModal(row, 'log')`) rather than an in-place
  editor — Page A's "no modal" principle was specific to *active* ISBAR
  entry; the doc's Page C decisions don't ask for modal-free editing,
  only that the *preview pane* stay inspection-only.
- `view-log-patient-details`/`edit-log-patient` (the old History tab's
  actions on `patient-details-modal`) are now unreachable dead code —
  nothing in the UI renders a log-sourced row through that path anymore.
  Left in place rather than deleted this late in the pass; a real,
  bounded cleanup opportunity for later, not a functional gap (the
  modal's *daily*-row path, used by Page A's "View" button, is
  unaffected and still fully exercised by `patient-details.spec.js`).
- Pre-existing non-admin dev accounts (`triage`, `test`) had `patients`
  in their granted sections, which used to implicitly include the
  History tab. Splitting History into its own section would have
  silently revoked their access, so both accounts were updated (via
  `PUT /api/auth/users/{id}`) to also grant `patient-history` — a real
  access-migration consideration from turning one page into two, not
  something to leave for someone to notice was broken later.

**Real bug found by running the suite, not by inspection**: History's
table rows initially reused the `.pat-row` CSS class (for its existing

set — every row click fired both listeners, and the stray one called
`openPatientDetailsModal(NaN)`, which rendered an error state that then
blocked all further clicks in an automated screenshot check. Fixed by
giving History's rows their own `.hist-row` class (with equivalent
styling) instead of borrowing Page A's.

## Post-close user feedback, 2026-09-22 — Page A field cleanup + Page B icon size

Two rounds of direct user feedback after the closing summary above,
both acted on immediately.

**1. Page A's Patient & Arrival section had two fields no user ever
fills in, and Triage Time asked for a date it doesn't need.**
- Removed **Departure Time** and **Bed Occupation Time** inputs from
  Page A entirely — neither is ever typed at ISBAR-entry time:
  departure only exists once a discharge actually happens (Beds
  Display / Unurgent discharge modals), and bed occupation is set by
  the real bed-assignment action (`assignPatientToBed()` in
  `beds_display.js`), not here. `patAutoOccupation()` (the function
  that used to silently copy Arrival Time into the now-removed field)
  was deleted as dead code.
- **Real data-loss risk found and fixed while doing this**:
  `PatientManager.modify()` overwrites `bed_occupation_time`
  unconditionally on every PUT `/modify` call — it doesn't coalesce
  with the existing value. Simply removing the input and always
  sending `null` would have silently wiped out a real bed assignment
  the very next time a nurse saved an ISBAR note on Page A. Fixed by
  caching the loaded record's real `bed_occupation_time` in a new
  `patActiveBedOccupationTime` variable (set in `selectPatStay()`) and
  resending that unchanged value on every save, instead of reading a
  form field that no longer exists. Proven with a new Playwright test
  in `isbar-form.spec.js`: assign a bed via the real API, save an
  unrelated vital from Page A, confirm `bed_occupation_time` survives.
- **Triage Time** is now a time-only picker (`dt-picker-time`, a new
  variant added to `datetime-picker.js` alongside the existing
  full-datetime one — `enableTime:true, noCalendar:true,
  dateFormat:'H:i'`) — asking for a date was pointless noise since
  triage always happens the same day as arrival, and the value is used
  purely to compute a wait duration (`hours since arrival`), not
  displayed as a calendar date anywhere. The bare "H:i" the picker
  produces is combined with Arrival Time's own date
  (`_combineWithDatePart()`, new helper in `patients.js`) before it's
  sent anywhere expecting a full timestamp, and split back out
  (`_extractTimeHHmm()`) when loading an existing value into the
  picker — so every other part of the app (wait-time threshold checks,
  History's display, the database column) still sees a normal full
  timestamp; only the *input UI* changed.

**2. Page B's unified card icon was too small — user wanted the old
bed graphic's at-a-glance presence back.**
The unified card (UI-B1) originally gave the bed/waiting icon a small
15px corner glyph, prioritizing a clean flat layout over visual
punch. Feedback: bring back the sense of scale the old decorative
pillow/mattress/frame bed graphic had — important for reading the
board at a glance, especially in "Fit to Screen" kiosk mode on a wall
monitor. Fixed by bumping `.erb-card-icon` to 30px at near-full
opacity (`beds.css`) — same unified component, same one-line CSS
change applies to both bed and waiting cards equally (confirmed
decision #5 still holds: only the icon and status treatment differ).

**Verification**: full Playwright suite re-run 2× after all of the
above landed — `22 passed` (0 failed) both times, including the new
bed-occupation-time regression test. Visually confirmed via real
screenshots: Page A's Patient & Arrival section now shows only Patient
ID/Stay ID/Name/Gender/Age/Arrival Time/Triage Time in the top row
(Departure/Bed Occupation gone), the Triage Time picker opens as a
plain hour:minute widget with no calendar, and Page B's bed icons
render clearly larger.
