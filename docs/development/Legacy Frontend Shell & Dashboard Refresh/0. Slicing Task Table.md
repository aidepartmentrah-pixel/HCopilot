## Background

Source notes: `source/Theme Edits.md` and `source/Dashboard Edit.md`
(copied verbatim from the user's own files, originally under
`Desktop/Slight Edit to the Old HCopilot/`).

**Both workstreams target the OLD (legacy) vanilla HTML/CSS/JS
frontend under `frontend/`, not the new React/TypeScript app under
`New Frontend (React Rewrite)`.** This was confirmed explicitly by the
user after some back-and-forth:

- `Theme Edits.md` is unambiguous on its own — it explicitly scopes
  itself to "the existing vanilla HTML/CSS/JavaScript HCopilot
  frontend" and explicitly forbids introducing React/TypeScript/Vite.
- `Dashboard Edit.md` is written in React terms (component names like
  `DashboardPage`/`MetricCard`, "Lucide React" icons) because it was
  originally drafted for the new frontend. The user wants its
  *ideas* — operational KPIs, a real welcome panel, activity/alerts/
  status panels — pulled out and re-slotted onto the **old**
  frontend's Home page instead, translated to vanilla JS render
  functions and local static SVG icons (no React, no component
  library).

Both source docs describe a React-flavored implementation
(`DashboardPage`, `MetricCard`, "Lucide React"); every slice below
reinterprets that as vanilla HTML/CSS/JS work against the existing
`frontend/js/*.js` + `frontend/css/*.css` + `index.html` pattern
already used throughout this codebase (e.g. `patient-details-view.js`'s
pure data-builder + render-function split is the model to follow, not
a new component framework).

- Manual browser screenshot check for at least one slice per new visual
  surface (theme switch, each new dashboard panel) before calling it
  done, same discipline as the ER redesign's bed-graphic/tabs/sticky-
  pane rounds.

## UI-T1 — Central CSS design tokens, 2026-09-22

Extracted the hardcoded purple brand colors scattered across the
legacy frontend's CSS into a `:root` token block at the top of
`frontend/css/base.css`:

```css
:root {
    --brand-500: #667eea;
    --brand-600: #764ba2;
    --brand-700: #5a67d8;
    --brand-800: #6b46c1;
    --brand-accent: #4f46e5;
}
```

Real scope found by grepping, not assumed: 111 raw occurrences of these
5 hex values across **14 CSS files** (`auth.css`, `base.css`,
`beds.css`, `datasets.css`, `datetime-picker.css`,
`flow_prediction.css`, `home.css`, `modals.css`, `models.css`,
`patients.css`, `scheduling.css`, `settings.css`, `simulation.css`,
`statistics.css`) — all mechanically replaced with `var(--brand-*)`
references. Out of scope for this slice (left as-is, to revisit when
UI-T2/UI-T6 actually change these): a handful of `rgba(91,103,216,...)`
shadow/overlay values that are hand-decomposed RGB equivalents of the
same brand color rather than the hex literal itself.

**Bug caught before shipping**: the bulk `sed` replace was run in two
passes (one per new file, one to catch remaining occurrences in
`base.css` itself) — the second pass matched the token *definitions*
too, turning `--brand-500: #667eea` into the circular
`--brand-500: var(--brand-500)`, which is invalid CSS and would have
silently broken the entire brand palette (invalid custom properties
resolve to their inherited/initial value, so the whole header/button/
background system would have gone transparent or unstyled). Caught by
grepping for the `--brand-*: var(--brand-` self-reference pattern
before rebuilding, fixed by restoring the literal hex values in the
`:root` block only. Worth remembering for T2/T6/T7: any bulk CSS
find-replace touching a file that also *defines* the thing being
replaced needs a self-reference check afterward.

**Verified for real:**
- `docker compose build frontend && docker compose up -d frontend` —
  built and started clean.
- Screenshot of the logged-in Home page at 1440×900 — visually
  identical to before the refactor (same purple header/background
  gradient, same button colors, same active-nav state) — pure token
  extraction, zero visual change, as intended.
- Full Playwright suite: **25/25 passed** (1.0m), no regressions.

Next: UI-T2 (navbar visual restyle) is the first slice with an actual
visual change — will screenshot before/after and check with the user
before calling it done, same as every other visual decision in this
project.
